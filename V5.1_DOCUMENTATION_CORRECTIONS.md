## CORRECTION 1: Firestore Query/List Behavior

### V5 Incorrect Statement

```
"For each document:
  - Evaluates: allow read: if isUserActive()
  - Calls: get(/users/{uid})
  - Checks: status == 'active'
  - Filters out documents where user not active"
  
"Result:
  - Active user: gets all diary
  - Disabled user: empty result set"
```

**Problem:** Implies rules filter documents (they don't). Rules are authorization checks, not filters.

### V5.1 Corrected Statement

```
ACTUAL FIRESTORE RULES BEHAVIOR:

Rules are authorization checks, not filters. When a rule denies access:

FOR EACH DOCUMENT:
  1. Firestore evaluates: allow read: if isUserActive()
  2. Calls: get(/users/{uid})
  3. Checks: status == 'active'
  4. If DENIED (status != 'active'):
     - Document NOT included in results
     - Query fails with: "PERMISSION_DENIED"
     
NOT: Documents filtered and returned as empty result
NOT: Unauthorized documents returned separately
ACTUALLY: Query throws error if ANY document authorization fails

EXPECTED BEHAVIOR FOR DISABLED USER:

Frontend Query:
  db.collection('diary').get()

Firestore Processing:
  - Fetches documents from collection
  - Evaluates read rule for FIRST document
  - isUserActive() returns false (status='disabled')
  - Query fails immediately

Backend Response:
  error: {
    code: 'permission-denied',
    message: 'Missing or insufficient permissions'
  }

Frontend Handling:
  Frontend MUST handle the error:
  
  db.collection('diary').get()
    .then(snap => { /* success */ })
    .catch(error => {
      if (error.code === 'permission-denied') {
        // User does not have access to this collection
        // Check user status via /users listener
        // Show message: "You do not have access to this content"
      }
    })

NOT EXPECTED:
  ✗ Empty result set { docs: [] }
  ✗ Unauthorized documents in results
  ✗ Silent filtering

HOW TO TEST:
  1. Use Firestore Rules Emulator (firebase emulators:start)
  2. Create test user with status='disabled'
  3. Query /diary collection
  4. Verify: query throws 'permission-denied' error
  5. Confirm: no documents returned
  6. Confirm: error thrown immediately (not silently filtered)
```

### Implementation Note for Frontend

```
CURRENT: Frontend does NOT handle permission-denied from diary/exams queries
         (Because today, all users can read - no auth on collections)

POST-MIGRATION: Frontend must handle permission-denied
  
  const handleDiaryQuery = async () => {
    try {
      const snap = await db.collection('diary').get();
      // Display diary
    } catch (error) {
      if (error.code === 'permission-denied') {
        console.log('User cannot access diary');
        // Rely on listener to show "Account disabled" message
        // OR redirect to home/login based on /users status
      } else {
        console.error('Query error:', error);
      }
    }
  };
```

### Documentation Change Summary

**Remove:**
- "Filters out documents where user not active"
- "Disabled user: empty result set"

**Add:**
- "Query throws 'permission-denied' error if authorization fails"
- "Frontend must handle error in catch block"
- "No silent filtering - error indicates no access"
- "Test with Firestore Rules emulator to verify behavior"

## CORRECTION 2: Performance/Billing Claims

### V5 Incorrect Statements

```
"Each get() call is a Firestore read (billable).
But: Results cached within a request context.
So: 100 diary docs for same user = 1 get(/users) call + caching
Result: Minimal overhead"

"Cost: Variable (1-100 reads depending on unique users)"

"Cost: 1 get per unique user"
```

**Problems:**
1. Claims rules caching guarantees (unverified)
2. Claims specific billing outcome as fact
3. No distinction between evaluation caching and actual billing

### V5.1 Corrected Statements

```
FIRESTORE GET() CACHING AND BILLING:

RULES EVALUATION CACHING (within request):
  - Firebase MAY cache get() results during rule evaluation
  - If multiple documents need same /users/{uid} check
  - Within SINGLE query execution: may share cached result
  - This is implementation detail (not guaranteed)
  
FIRESTORE BILLING:
  - Each get() in rules = billable read operation
  - Caching behavior does NOT guarantee billing reduction
  - "Cached" get() may still be billable (exact behavior TBD)
  - Cannot assume: "100 docs = 1 read"
  
ACTUAL COST: REQUIRES TESTING
  - Exact billing behavior depends on Firebase implementation
  - Must verify with:
    1. Firestore Rules emulator (check read count)
    2. Firebase production billing (actual results)
    3. Query patterns in actual app (not theoretical)

VERIFICATION NEEDED:
  Test Case 1: Single user queries 100 diary documents
    Expected: isUserActive() called 100 times
    Question: How many billable get(/users/{uid}) calls?
    How to test: 
      - Run in emulator with query
      - Check get() call count in logs
      - Check billing simulation
    
  Test Case 2: 100 users each query 1 diary document
    Expected: isUserActive() called 100 times
    Question: 100 different get(/users/{uid}) calls?
    How to test:
      - Parallel queries from different users
      - Check get() call count
      - Check billing

REALISTIC ASSUMPTIONS (not guarantees):
  - Per-unique-user get() likely (not per-document)
  - Caching within request context may reduce calls
  - First user: 1 get(/users) + 1 per document (potentially)
  - Repeated user: may reuse cached result
  - Actual behavior: VERIFY before production

RECOMMENDATION:
  Before production deployment:
    [ ] Test queries in Firestore emulator
    [ ] Measure get() call counts
    [ ] Verify with actual query patterns
    [ ] Check Firebase billing documentation
    [ ] May adjust queries if costs unacceptable
```

### Documentation Change Summary

**Remove:**
- "So: 100 diary docs for same user = 1 get(/users) call"
- "Result: Minimal overhead"
- "Cost: 1 get per unique user"

**Add:**
- "Rules evaluation MAY cache get() results (unverified)"
- "Billing impact: REQUIRES TESTING"
- "Cannot assume reduced costs without verification"
- "Must test in emulator and production"
- "Query patterns in actual app will determine real cost"
